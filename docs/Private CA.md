# AWS Private Certificate Authority (Private CA)

## a) What This Service Is and When to Use It
AWS Private Certificate Authority (AWS Private CA) is a managed private CA service that helps you easily and securely manage the lifecycle of your private X.509 certificates. It allows organizations to build and maintain their own internal Public Key Infrastructure (PKI) hierarchy without the investment and operational maintenance costs of operating on-premises hardware security modules (HSMs) and CA software. You should use AWS Private CA when securing internal microservices, private VPC network endpoints, VPN connections, IoT devices, and corporate intranet applications with SSL/TLS certificates that do not require public Web trust. It integrates directly with AWS Certificate Manager (ACM) to issue and automatically renew private certificates across your AWS resources.

## b) Key Concepts

### 1. Root Certificate Authority (Root CA)
The top-most Certificate Authority in a public key infrastructure hierarchy. A Root CA signs its own certificate (self-signed) and acts as the ultimate trust anchor for all subordinate CAs and end-entity certificates issued downstream in the organization.
- *Example*: `CN=Corp Root CA, O=Example Enterprise, C=US` installed with a 10-year validity period as the trust root for internal company infrastructure.

### 2. Subordinate Certificate Authority (Subordinate CA)
A CA whose certificate is issued and cryptographically signed by another CA higher in the hierarchy (either a Root CA or an intermediate Subordinate CA). Subordinate CAs are commonly used to segment certificate issuance by environment, department, or geographic region.
- *Example*: `CN=Corp Production Sub CA, O=Example Enterprise, C=US` signed by the Root CA to issue server certificates strictly for production Kubernetes clusters.

### 3. Certificate Signing Request (CSR)
A standardized, cryptographically signed file generated by the CA that contains its public key and distinguished name (DN). The CSR is exported to be signed either by the CA itself (for Root CAs) or by an external/parent CA to produce the CA certificate.
- *Example*: Exporting the PEM-encoded CSR from a newly created CA to sign it using OpenSSL or an enterprise parent CA.

### 4. CA Certificate Installation and Activation
When created, a CA enters the `PENDING_CERTIFICATE` status. To become `ACTIVE` and capable of issuing end-entity certificates, you must import an imported or self-signed certificate into the CA.
- *Example*: Generating a self-signed root certificate using the `RootCACertificate/V1` template and importing it into the CA to transition its status from `PENDING_CERTIFICATE` to `ACTIVE`.

### 5. Certificate Templates
Pre-configured X.509 extension profiles provided by AWS Private CA that specify allowable key usage, extended key usage, and constraints for issued certificates.
- *Example*: Using the `EndEntityCertificate/V1` template to issue a TLS server and client authentication certificate, or `SubordinateCACertificate/V1` when creating an intermediate CA.

### 6. Certificate Revocation List (CRL) and S3 Revocation Configuration
A list of digital certificates that have been revoked by the issuing CA before their scheduled expiration date (for instance, when a private key is compromised). AWS Private CA generates and regularly uploads the CRL file to a designated Amazon S3 bucket.
- *Example*: An Amazon S3 bucket `my-company-ca-crl` configured with a custom prefix `crl/` to publish daily revocation lists accessible by internal network clients.

### 7. Deletion Retention Window (7 to 30 Days)
AWS Private CA protects against accidental destruction of your PKI infrastructure. When you delete a CA, it enters the `DELETED` state for a configurable grace period between 7 and 30 days (default is 30 days). During this window, certificate issuance is disabled, but you can restore the CA back to `DISABLED` state before it is permanently purged.
- *Example*: Scheduling a decommissioned development CA for deletion with a 7-day retention period.

## c) Walkthrough of the Console with Matching AWS CLI Commands

All commands below have been tested and verified against the local AWS Emulator running at `https://127.0.0.1:9297`.

```bash
# Set up your environment variables for emulator access
export AWS_ENDPOINT_URL="https://127.0.0.1:9297"
```

### 1. Private CAs Inventory Page (`/acm/pca` or `/pca`)
- Displays metric summary cards: Total Private CAs, Active CAs, Pending Certificate CAs, and Disabled CAs.
- Search input and dropdown filters for Status (`All statuses`, `Active`, `Pending certificate`, `Disabled`, `Deleted`) and Type (`All types`, `Root`, `Subordinate`).
- Interactive selection table showing Common Name, CA ID, CA Type, Status badge, Key Algorithm, Signing Algorithm, and Created / Expiration timestamps.
- Action toolbar with buttons: `Create private CA`, `Actions` dropdown (`View details`, `Install CA certificate`, `Issue certificate`, `Enable`, `Disable`, `Delete`, `Restore`), and `Refresh`.

*Matching AWS CLI Command*:
```bash
aws acm-pca list-certificate-authorities \
  --endpoint-url https://127.0.0.1:9297 \
  --ca-bundle ~/.aws/emulator/9297/ca.pem
```

### 2. Create Private CA Wizard (`/acm/pca/create`)
A multi-step configuration wizard matching the AWS Management Console:
- **Step 1: CA Type**: Choose between `Root CA` (self-signed trust root) or `Subordinate CA` (signed by an existing root or parent CA).
- **Step 2: Subject Distinguished Name (DN)**: Configure Common Name (`CN`), Organization (`O`), Organizational Unit (`OU`), Country (`C`), State/Province (`ST`), and Locality (`L`).
- **Step 3: Key Algorithms**: Select Key algorithm (`RSA 2048`, `RSA 4096`, `ECDSA P-256`, `ECDSA P-384`, `ECDSA P-521`) and Signing algorithm (`SHA256WITHRSA`, `SHA512WITHRSA`, `SHA256WITHECDSA`, etc.).
- **Step 4: Certificate Revocation List (CRL)**: Optional toggle to enable CRL generation. Select an Amazon S3 bucket from a live dropdown populated by the local S3 service, specify an S3 object prefix, and configure custom CNAME distribution points.
- **Step 5: Tags**: Add optional key-value metadata tags to the CA resource.
- **Step 6: Review & Submit**: Review all configurations and click `Create private CA`.

*Matching AWS CLI Command*:
```bash
aws acm-pca create-certificate-authority \
  --endpoint-url https://127.0.0.1:9297 \
  --ca-bundle ~/.aws/emulator/9297/ca.pem \
  --certificate-authority-type ROOT \
  --certificate-authority-configuration '{
    "KeyAlgorithm": "RSA_2048",
    "SigningAlgorithm": "SHA256WITHRSA",
    "Subject": {
      "Country": "US",
      "Organization": "Example Enterprise",
      "OrganizationalUnit": "Security",
      "State": "Washington",
      "Locality": "Seattle",
      "CommonName": "Corp Root CA"
    }
  }'
```

### 3. Install CA Certificate & Activate CA
Newly created CAs start in `PENDING_CERTIFICATE` status. The console opens an **Install CA Certificate** modal allowing:
1. **Self-signed Root CA Certificate**: Automatically generates a self-signed root certificate using the `RootCACertificate/V1` template for a specified validity period (default 10 years) and imports it into the CA to transition it to `ACTIVE`.
2. **External / Parent Signed Certificate**: Paste the certificate PEM body and optional certificate chain PEM to activate a subordinate or externally signed CA.

*Matching AWS CLI Commands*:
```bash
# 1. Get the CA's Certificate Signing Request (CSR)
aws acm-pca get-certificate-authority-csr \
  --endpoint-url https://127.0.0.1:9297 \
  --ca-bundle ~/.aws/emulator/9297/ca.pem \
  --certificate-authority-arn "<CA_ARN>" \
  --output text > /tmp/ca.csr

# 2. Issue a self-signed root certificate from the CSR
aws acm-pca issue-certificate \
  --endpoint-url https://127.0.0.1:9297 \
  --ca-bundle ~/.aws/emulator/9297/ca.pem \
  --certificate-authority-arn "<CA_ARN>" \
  --csr fileb:///tmp/ca.csr \
  --signing-algorithm SHA256WITHRSA \
  --template-arn "arn:aws:acm-pca:::template/RootCACertificate/V1" \
  --validity Value=3650,Type=DAYS

# 3. Retrieve the generated certificate PEM
aws acm-pca get-certificate \
  --endpoint-url https://127.0.0.1:9297 \
  --ca-bundle ~/.aws/emulator/9297/ca.pem \
  --certificate-authority-arn "<CA_ARN>" \
  --certificate-arn "<CERTIFICATE_ARN>" \
  --query Certificate \
  --output text > /tmp/ca.crt

# 4. Import certificate into the CA to activate it
aws acm-pca import-certificate-authority-certificate \
  --endpoint-url https://127.0.0.1:9297 \
  --ca-bundle ~/.aws/emulator/9297/ca.pem \
  --certificate-authority-arn "<CA_ARN>" \
  --certificate fileb:///tmp/ca.crt
```

### 5. Disable, Enable, Delete, and Restore CA

#### Disable / Enable CA
You can temporarily disable an active CA to block certificate issuance without destroying its configuration or keys. Disabling sets status to `DISABLED`. Enabling returns it to `ACTIVE`.

*Matching AWS CLI Command*:
```bash
# Disable CA
aws acm-pca update-certificate-authority \
  --endpoint-url https://127.0.0.1:9297 \
  --ca-bundle ~/.aws/emulator/9297/ca.pem \
  --certificate-authority-arn "<CA_ARN>" \
  --status DISABLED

# Enable CA
aws acm-pca update-certificate-authority \
  --endpoint-url https://127.0.0.1:9297 \
  --ca-bundle ~/.aws/emulator/9297/ca.pem \
  --certificate-authority-arn "<CA_ARN>" \
  --status ACTIVE
```

#### Delete CA (Soft Delete with Retention)
Opens a modal with a retention period slider between 7 and 30 days. Moving a CA to `DELETED` state preserves the CA and its serial logs during the retention window.

*Matching AWS CLI Command*:
```bash
aws acm-pca delete-certificate-authority \
  --endpoint-url https://127.0.0.1:9297 \
  --ca-bundle ~/.aws/emulator/9297/ca.pem \
  --certificate-authority-arn "<CA_ARN>" \
  --permanent-deletion-time-in-days 7
```

#### Restore CA
Restores a `DELETED` CA back to the `DISABLED` status. After restoring, you can inspect it and click **Enable** to resume issuing certificates.

*Matching AWS CLI Command*:
```bash
aws acm-pca restore-certificate-authority \
  --endpoint-url https://127.0.0.1:9297 \
  --ca-bundle ~/.aws/emulator/9297/ca.pem \
  --certificate-authority-arn "<CA_ARN>"
```

## d) Hands-on Exercises for Beginners

### Exercise 1: Create and Activate a Self-Signed Root Private CA
**Objective**: Provision your organization's first Root Certificate Authority and activate it.
1. In the console, navigate to **AWS Private CA** (`/acm/pca`).
2. Click **Create private CA**.
3. Choose **Root CA** and click **Next**.
4. Set Common Name to `Internal Enterprise Root CA`, Organization to `My Corp`, and Country to `US`.
5. Keep default key algorithm `RSA 2048` and signing algorithm `SHA256WITHRSA`.
6. Leave CRL optional, add a tag `Environment=Demo`, review, and click **Create private CA**.
7. In the CA table, observe the new CA in `Pending certificate` status.
8. Select the CA, click **Actions > Install CA certificate**, choose **Self-signed root CA certificate** with validity `10 years`, and click **Install and activate**.
- **Expected Result**: The CA status badge turns green (`Active`). The Overview tab shows valid Not Before and Not After timestamps.

---

### Exercise 2: Issue an Internal End-Entity TLS Certificate
**Objective**: Issue a private certificate for an internal microservice.
1. Click into your active Root CA to open its details page.
2. Select the **Issue Certificate** tab.
3. Paste a valid CSR PEM (or use the provided sample CSR).
4. Choose template `EndEntityCertificate/V1` and validity `365 DAYS`.
5. Click **Issue certificate**.
- **Expected Result**: A success notification appears with the Certificate ARN. The page displays the Certificate PEM and Certificate Chain PEM with buttons to copy them directly to your clipboard.

---

### Exercise 3: Revoke a Compromised Certificate
**Objective**: Invalidate an issued certificate by publishing its serial number to the revocation list.
1. On the **Issue Certificate** tab, scroll to the **Revoke Certificate** section.
2. Enter the serial number of the certificate you issued in Exercise 2.
3. Select Revocation reason: `KEY_COMPROMISE`.
4. Click **Revoke certificate**.
- **Expected Result**: A confirmation banner confirms the certificate has been marked revoked with reason `KEY_COMPROMISE`.

---

### Exercise 4: Disable, Soft-Delete, and Restore a Private CA
**Objective**: Practice safe decommission and disaster recovery procedures.
1. From the CA details page or table, click **Actions > Disable**. Verify the status changes to `Disabled`.
2. Click **Actions > Delete**. In the modal, select a retention window of `7 days` and confirm deletion.
3. Notice the CA status updates to `Deleted`.
4. Select the CA and click **Actions > Restore**.
5. Once restored to `Disabled`, click **Actions > Enable** to return it to service.
- **Expected Result**: The CA returns safely to `Active` status without losing any historical metadata, keys, or issued certificates.

## e) Limitations in the Local Emulator

While the local emulator provides a high-fidelity implementation of the AWS Private CA API, learners should be aware of the following local environment differences:

1. **Hardware Security Modules (HSM)**: In AWS production, Private CA stores private keys in FIPS 140-2 Level 3 validated hardware security modules. The local emulator generates and stores cryptographic keys locally in its memory and disk cache.
2. **OCSP (Online Certificate Status Protocol)**: The local emulator does not run a dedicated public OCSP responder daemon. Revocation validation should be tested via CRLs.
3. **Automated ACM Certificate Renewal**: On real AWS, private certificates requested via ACM and issued by an AWS Private CA can be automatically renewed when used with AWS services like ALB or API Gateway. In the local emulator, renewals must be triggered manually via API.
4. **S3 Bucket for CRL**: When enabling CRL generation, the designated S3 bucket must already exist in your local emulator; if the bucket does not exist, the emulator will accept the configuration but cannot write CRL objects.

## f) Common Errors and Troubleshooting

### Error: `InvalidStateException: The certificate authority must be in the ACTIVE or DISABLED state to be updated`
- **Cause**: Attempting to call `update-certificate-authority` (e.g. enabling or disabling) while the CA is still in `PENDING_CERTIFICATE` status.
- **Solution**: Install and import a CA certificate first using **Install CA certificate** to activate the CA before attempting to change its operational status.

### Error: `ValidationException: Member must satisfy regular expression pattern: -----BEGIN CERTIFICATE-----\r?\n...`
- **Cause**: The imported certificate PEM string has malformed line wrapping, missing header/footer markers, or escaped literal `\n` characters instead of real newline linebreaks.
- **Solution**: Ensure your PEM certificate begins with `-----BEGIN CERTIFICATE-----`, ends with `-----END CERTIFICATE-----`, and contains standard 64-character base64 lines separated by actual newlines.

### Error: `ResourceNotFoundException: The certificate authority does not exist`
- **Cause**: The specified CA ARN was misspelled or points to a different AWS Region or account ID.
- **Solution**: Verify the CA ARN using `aws acm-pca list-certificate-authorities` and ensure your active region is set to `us-east-1`.

### Error: `InvalidArgsException: Retention window must be between 7 and 30 days`
- **Cause**: When deleting a CA, `--permanent-deletion-time-in-days` was set to less than 7 or greater than 30.
- **Solution**: Specify an integer between 7 and 30 (inclusive) in the deletion retention slider.
